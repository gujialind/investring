- **满足下限**：6 个 PR ≥ 3，10 个 run，57 条原稿条目 / 50 条发布条目。
- **足以判定**：① 过滤能拦住误报（5 次拦截、4 种不同否证手法，均可回溯原句）；② 同 head 重跑的召回/定级不稳定（720 三轮是硬证据，`6206414476` 自述已把这当作不采信单次「通过」的理由）；③ 压缩发布有破坏性（15 条发现被删 §6.1 必需字段）。
- **不足以判定**：① 过滤的**净收益**（无「不过滤直接发布」的同 PR 对照，735/737 只有 3 条且 PR 类型不同）；② 拦截率、修正率的置信区间（5 条拦截 / 1 条逃逸，单条变化即 ±8~17pt）；③ 压缩与逐字两种发布形态对**采纳率**的影响（本轮采纳率 93.1%，两个压缩 PR 的 15 条全部为 A，样本内无法区分）。
- **继续试点的最小样本建议**：
  - 结构：**同一 head 上「过滤发布」与「原稿直发」成对**，至少 3 对（即 3 个 PR × 2 种发布），否则净收益不可估。
  - 规模：**≥10 个 PR / ≥15 个 run / 原稿条目 ≥100**，使误报逃逸率的分母 ≥8（本轮逃逸仅 1 条）。
  - 必须新增记录（否则下轮仍只能估算）：`--no-post` 出稿完成时刻、编排侧核实开始/结束时刻、发布时刻 —— 三个时间戳写入 manifest，把「SDK 时长」与「过滤时长」分开计；以及每条「撤回/不采纳」主张的结构化字段（`claim`/`refuter`/`evidence_anchor`）。
  - 级别要求：过滤新增条目必须带 `[Blocker]/[Suggestion]/[Nit]`，以消除本轮 2 条目检新增造成的口径空洞。

## 8. 试点结论（值不值得固化）

**值得固化，但只固化「关口 + 留痕」，不固化「压缩」。**

| 观察 | 处置建议 |
| --- | --- |
| 5 次误报拦截全部靠**读原文/读模型约束/读既有测试口径**，成本与 R2 的位置核验同量级 | 固化为发布前必做（`report.md` R2、流程建议 §6.2 第 3 条） |
| 3 个 run 逐字全等发布（720-r3、727-r2、728-r2），证明「过滤」不必改写正文 | 固化「逐字发布」为默认，压缩需显式授权 |
| 2 个 run 压缩发布删掉 §6.1 的 `触发与证据`/`验证`（15 条），复盘可行性下降 | **不要固化压缩形态**；先定最小字段（R1） |
| 720-r2 整轮未发布、内容被跨轮消费，只在自述里间接可见 | 固化「整轮未发布必须在 issue 留痕轮次/head/原因」（R1 后半句） |
| 同 head 三轮定级不一致（`records_success` 在 run1=Blocker、run2=Nit） | 固化「Blocker 候选 ≥1 时至少重跑一次并合并两轮结论」（流程 §6.2 第 4 条） |
| 过滤新增 2 条无级别 → 不计发现，却真实驱动了 2 个修复 commit | 固化「过滤产出的新条目必须带级别」（R1 / 试点最小样本第 4 条） |
