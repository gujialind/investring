### 4.3 ≥5pt 差异的可能原因（不只报数字）

采纳率 +17.4pt（主因排序）：

1. **发布前过滤改变了「什么被发布」**（最强解释，见 `pilot.md`）。本轮 6 个 PR 走过滤，10 个 run 的原稿 57 条 → 发布 50 条：剔除 7 条、改写/压缩 17 条、拦截误报 5 条（复核子代理提出的 5 条主张经实读/实跑否证，从未成为发布条目）。基线 38 条**没有这道关口**（#722 把「发布前过滤」列为缺口即为此）。这直接压低了 B2/C 在分母中的占比 —— B2 从 13.5% 降到 1.72% 与此机制吻合。
2. **发现构成偏向「可验证的一致性」类**：58 条中 19 条对象是文档/规则正文、9 条是契约口径（`settled`/`pair_ref`/错误码总表/`flow_type`）。这类发现的对错是二值的、修复动作就是改同一份文件，采纳成本极低；基线则以行为类/测试类为主，B2 高发于「建议加防御但无实际收益」。
3. **核验强度变化（度量端而非评审端）**：本轮 58/58 读码核验，基线为 chain-only。这不改变真实质量，但会**改变观测**：本轮新识别出 1 条 C（`723-5`）与 2 条 PREMISE PARTIAL（`726-5`/`727-1`），基线口径下同类问题可能仍留在 A 里。故错误率 +1.72pt 更可能反映「看得更清」，不宜解读为质量下降。
4. **样本量**：58 vs 37。单条 C 即 1.72pt，单条误判即 ±1.7pt；置信区间宽，不宜把 1.72% 与 0.0% 当作有实质差别。

不是主因的候选（已排除）：

- **PR 类型构成变化**：本轮新纳入 3 个纯文档 PR（728/735/737，基线 9 个 PR 全是行为/代码 PR）。若文档 PR 采纳率显著更高，构成本身就能解释提升。实测：代码/行为 5 PR 43 条采纳率 93.0%，纯文档 3 PR 15 条 93.3%，全表 93.10% —— **三者几乎相同，构成不是驱动因素**。

真问题率 −1.72pt 与 B2 占比 −11.8pt：与原因 1、2 同源（关口 + 构成）。单 PR 均值 +3.05 条：727（17）与 728（12）两轮各占一半，主因是这两 PR 分别做了首轮 + 第二轮全量审，第二轮新增 7 条与 5 条 —— 属轮次叠加，不表示同 head 的召回密度提升（同 head 三轮的 720 反而是「run3 无 Blocker、run1 的 2 条 Blocker 由编排侧改写发布」，见 `pilot.md` 第 4 节）。

## 6. 结论与建议（可执行）

### 6.1 评审规范条款草案（`docs/reference/code-review.md`）

**R1 — 发布前过滤的最小字段（新增，落点 §6.1）**
- 条款原文：§6.1「每条须给**级别、位置、触发条件、证据、影响与建议**，不能只说"改成 X"」；字段模板四行（影响与建议 / 位置 / 触发与证据 / 验证）。
- 拟改文本：在 §6.1 末尾追加一段 —「经**发布前过滤**（他人或另一会话逐条核实后再发布结论）时，允许压缩篇幅、合并 `触发与证据`/`验证` 两节，但每条发现仍须保留：级别、位置（`文件:行`）、成立判据（读码/实跑的结论词，如「实读确认」「变异后仍全绿」）、以及**未成立主张的撤回记录**。整轮不发布也须在 issue 留痕轮次、head 与未发布原因。」
- 依据：`pilot.md` 显示 726 与 727-r1 两跑压缩发布（−74.8% / −81.8%，合计 −14063 字符，占全部减量 99%）**整体删除了 §6.1 必需的 `触发与证据`/`验证` 字段**，涉 15 条发现；另有 720-r2 整轮 6 条未发布、仅在 `6206414476` 以自述痕迹（`851 passed`）间接可见。本轮 58/58 读码核验之所以能做，靠的是发布稿仍保留位置锚点 —— 若锚点也被压缩，复盘将不可行。
- 代价：极低。发布稿长度上限不变，只规定「不可删的三要素」；不新增工具。
- 需在 #722 增 checkbox：是（「为压缩发布定义最小字段」）。

**R2 — 位置核验作为发布前置闸（修订 §6.1 一句）**

### 6.2 流程建议（关口位置 / 执行者 / 必核级别 / 抽检）

1. **关口位置**：过滤放在「评审出稿」与「发布为 PR 评论」之间，不放在合入确认之后。判据：本轮 3 个逐字发布轮次（720-r3、727-r2、728-r2）与原稿完全一致，说明关口有效只需在发布前一次；若放到合入后，压缩发布删掉的字段无法复原（R1）。
2. **执行者**：编排侧（非出稿会话）执行，沿用现有分工表述 —— §1「审查者不直接改作者分支」、§6.1「不得把作者/CI 的结果写成自己实跑」。**必须写清核实者是审查者本人还是第二代理**，并在结论字段区分「审查者实跑 / 编排侧核实 / CI」。
3. **必核级别**：Blocker 与「拟撤回复核子代理主张」的条目 100% 核实（本轮 4 Blocker 全部由读码或实跑复现支撑，`6206414476` 的 P2 还给出 `('partial_success', 1, -49, 50)` 实跑返回值）；Suggestion/Nit 抽检 ≥30%，且**位置核验（R2）全量**，因为它是唯一可机械化的检。
4. **抽检比例与召回**：同 head 重跑时不默认取「无 Blocker」的那轮 —— `6206414476` 自述「`records_success` 相关的同类问题在另一轮实跑评审里被判为 Nit，说明自动评审的严重度判定跨轮次不稳定，单次『通过』不可直接作为放行依据」，本轮实测（720 三轮）证实该结论。建议：Blocker 类候选 ≥1 时至少重跑一次并合并两轮结论。
5. **单轮通过不作放行依据**：把上述表述写进 §5.3 合入条件的一句附注，不新增门禁。

### 6.3 度量自动化（可复跑步骤 + 最小脚本设计，不要求实现）

复跑步骤：

1. 枚举 merged PR：`gh pr list --state merged --json number,mergedAt,headRefOid,baseRefName,changedFiles`（本会话禁止 `gh`，脚本设计里保留）。
2. 每 PR 取 issue 评论 + review + 行内评论，按 `########## COMMENT <id> | <时间> | <字符数> ##########` 同构的分段格式落 `data/<pr>.txt`（本轮已用该格式）。
3. 抽取：正则 `^\[(Blocker|Suggestion|Nit)\]` 切条 + 抓 `位置：` 行的 `文件:行`；去重键 = (规范化标题前 40 字, 位置文件)。
4. **声明数核对**：解析结论字段 `发现：Blocker X / Suggestion Y / Nit Z`，与抽取数逐 PR 比对，差值非零即列出该 PR 全部无级别条目（本轮 8/8 一致，说明该检可自动化）。
5. 标注：verdict ∈ A/B1/B2/C/D + `verification` ∈ code_verified/chain_only/unverifiable（人工填，字段用 JSON Schema 钉住）。
6. 核验：对每条 `code_anchor` 跑 `git show <head>:<path>`，`awk` 取锚点行，检查（a）文件行数 ≥ 锚点行号，（b）该行含发现所述符号 → 不一致自动打 PARTIAL_ANCHOR 待人工裁。
7. 统计：`Counter` 输出 §4 全部指标，并与上一版 `findings.jsonl` 做 diff。
8. 漏报：`git log --since=<mergedAt> --until=<+72h> --grep='fix\|修复\|hotfix\|revert\|回归' -i --name-only` × 该 PR 文件面，排除本 PR 分支 sha（用 `git rev-list <reviewHead>..<mergeSha>` 判归属），输出候选供人工归因。

最小脚本：单文件 `scripts/review_metrics.py`（或复盘目录内脚本），子命令 `extract` / `check-declared` / `verify-anchors` / `missed` / `stats`；只依赖 stdlib + git；输入 `data/` + `repo/`，输出 `out/findings.jsonl` 骨架与 `out/metrics.json`。安全边界：脚本内 git 只允许 `show/log/diff/grep/cat-file/rev-parse/ls-tree`，其余子命令直接抛错。`review-retro-722` 本次已用等价的一次性脚本复算全部计数，可作参照实现。
