# 代码审查标准与流程

> 本文定义 InvestRing 的**代码审查判定标准**（看什么、怎么定级）与**流程**（谁在哪一步做什么、结论如何处置）。
> 定位：根 `AGENTS.md` §3 定义开发流程骨架（分支/issue/PR/commit），本文只细化「审查」这一环，不重复其内容。
> 相关：机械门禁清单见 `.github/workflows/ci.yml`；业务不变量见根 `AGENTS.md` §2 与 `docs/reference/business-constraints.md`；前端规范见 `docs/design/visual-spec.md`。

***

## 0. 为什么需要这份标准

本仓库的机械门禁已经很厚：CI 全部 job 加 `CI OK` 汇总门禁（后端 SQLite/MySQL 双跑、CLI 契约漂移、前端 lint+tsc+单测+build、E2E、E2E 形态对比、scripts 单测、Docker 构建冒烟；job 清单以 `.github/workflows/ci.yml` 为准）、覆盖率 `fail_under` 棘轮、`openapi.json` 与 `ir-cli` 响应字段契约防漂移、错误码↔文档一致性守门、ESLint AST 护栏（色板/任意值/数值展示/e2e 定位器）。

> ⚠️ **本文刻意不写 job 数量、覆盖率阈值等易漂移的具体数值**——第一版曾写「六个 job」「`fail_under=80`」，三天内即双双失实（#410 扩容 CI、#405 把阈值棘轮到 82）。数值一律指向源码，本文只陈述**判定口径**。

但**语义判决仍依赖临场发挥**，这是「质量参差不齐」的直接成因：

* 截至 2026-09-11 的抽样：近 300 次提交含 59 次 PR 合并，大量缺陷以「PR #X 评审 follow-up」形式补上。审查确实在起作用，**但标准从未被写下来**——换个会话、换个审查者，关注点就不同，结论不可复现。
* 高频缺陷高度集中在 CI 结构上拦不住的五类，全部是「编译通过、测试全绿、语义错了」：

| # | 缺陷模式 | 本仓库实证 |
| --- | --- | --- |
| 1 | **静默失败** | 以「静默」为关键词可检索到 30 余条 issue：#354（E2E 静默 skip 致覆盖蒸发）、#203（异常被吞产生孤儿快照）、#305（auto_confirm 失败与告警在多条路径静默丢失）、#417（stdout 单行 JSON 日志契约被两处未记录的明文来源破坏）、#234（产品页静默截断）、#235（负值被静默钳制为 0）、#231/#236（入参被静默覆盖） |
| 2 | **同源漏网** | #387 修了 `ProductFilterSelect` 空值守卫，#393 才发现 `ProductFilterDialog` 同源未修；#349 是 #249「全站清零」的遗漏；#382 的教训更直接——当年以「grep 零残留」验收，该结论从无机器保障且实际不成立 |
| 3 | **数值口径不一致** | #428（4 位小数缺省 `ROUND_HALF_EVEN` 与声明的 `ROUND_HALF_UP` 不符，7 处站点）、#421（审计载荷 `float()` 掉 DECIMAL 标度）、#190（场内卖出未推导 `amount`，配对 CASH 腿落成 0） |
| 4 | **文档-代码漂移** | #237（§7.2 已过时）、#418（错误码清单长期只覆盖 81 个在用码中的 26 个，**已补 AST 守门**）、#420（回滚速查表缺 5 行） |
| 5 | **覆盖无声蒸发** | #354 / #371 / #372 / #382 —— CI 绿，但断言早已不存在或从未生效 |

> 上表是**历史实证 + 模式识别**，不是当前缺口清单：其中 #418（错误码守门）、#420、#421、#422、#428 等均已修复并补了守门（见 §3.1 Q4）。列在此处是因为**模式会复现**——同一类缺陷在新代码里反复出现，正是通用五问存在的理由，也正是 §4.7 复盘闭环要把它们逐步下沉为机器门禁的原因。

* **结论：审查的价值不在于重复 CI，而在于专攻「绿而错」。** 本文第 3 节把这件事固化成可执行的清单。
* 反面约束同样重要：审查评论里出现「lint 报错」「CI 挂了」「类型不通过」属**无效评论**——那是机械门禁的职责，作者推一次就能看到。占用了审查注意力，就稀释了对上述五类的覆盖。

## 1. 三层防线与职责边界

| 层 | 执行者 | 管什么 | **明确不管** |
| --- | --- | --- | --- |
| **L0 自审** | 作者（人 + AI） | 读完整 diff、跑影响面测试、答通用五问、填自审清单 | 重复推导实现细节 |
| **L1 机械门禁** | CI（自动） | 语法/类型/构建、单测/集成/E2E、契约漂移、迁移可逆性、覆盖率阈值、依赖漏洞、静态规范（ESLint AST） | **意图与语义**——它只能判断「与既有规则冲突」，不能判断「这次是不是想错了」 |
| **L2 语义审查** | 审查者（以 AI 审查为主，人做终裁） | 第 3 节全部清单：意图自洽、失败可见性、同源覆盖、数值口径、契约同步、可回滚性 | L1 已覆盖的一切 |

**核心原则**：L1 能判的，L2 一概不判。每一层只补上一层结构上补不了的洞。

```
L0 作者自审（读 diff · 跑影响面 · 答五问）
   │
   ▼
L1 机械门禁（CI 全部 job + CI OK 汇总）
   │  红 ──────────────────────────────────▶ 回 L0
   │  绿
   ▼
L2 语义审查（专攻「绿而错」）
   │  🔴 打回 ─────────────────────────────▶ 回 L0
   │  🟡 开 follow-up issue ─┐
   │  通过 ──────────────────┤
   ▼                          ▼
合入 main ──▶ CD 自动部署
   │
   ▼
复盘：归类审查意见 ──▶ 反复出现的 ──▶ 下沉为 ESLint selector / CI 门禁
                                              │
                                              └──▶ 抬高 L1 水位（回到顶部）
```

最后一环是**本机制自我进化的闭环**：本仓库有此传统——#127 色板硬编码 → ESLint；#249 数值展示 → ESLint；#382 e2e 定位器 → ESLint。**审查意见是人肉门禁；同一意见重复出现，就说明它该变成机器门禁。**

## 2. 严重度分级

| 级别 | 含义 | 是否阻断合入 |
| --- | --- | --- |
| 🔴 **Blocker** | 会导致数据错误/丢失、资金口径错误、**静默失败**、契约破坏，且 CI 不会发现 | **阻断**，必须修复后重新审查 |
| 🟡 **Suggestion** | 应当修，但不影响正确性 | 不阻断；当场修，或按铁律开 follow-up issue |
| 💭 **Nit** | 可不修（命名、措辞、微调） | 不阻断；需在评论中明示「不修」的取舍 |

### 2.1 本项目的 🔴 判定线（照此对照，不靠感觉）

* **任何「失败被吞掉 / 降级为静默」的路径**——无日志、无告警、无异常出口。
* **数值产生点未量化，或舍入模式与根 `AGENTS.md` §2.11 不一致**（金额/份额 2 位、净值 4 位、`ROUND_HALF_UP`）；`float()` 掉 DECIMAL 标度。
* **服务层越过事务边界**：`app/services/**` 内 `commit`，或 import / 抛 `fastapi.HTTPException`（`backend/tests/unit/test_service_no_commit.py` 是守门，但新写法可能绕开）。
* **快照链路（snapshot / position / trade / subscription）改动缺影响面测试**——它是所有写路径的下游。
* **迁移缺可逆 `downgrade`**，或未过双方言（SQLite + MySQL），或未按 `create_all → alembic upgrade head` 顺序验证。
* **删除或放宽测试断言、新增掩盖失败的 `skip`**，只要 CI 仍绿就算覆盖蒸发。
* **破坏 API 契约而未同步** `openapi.json` / `ir-cli` response_fields（这类会被 CI 拦，但仍需在审查中确认语义变化是有意的）。
* **前端绕过统一口径**：直出数字不走 `format*` 系函数、份额不走 `formatSharesUnit`、红绿用于非盈亏语义（`docs/design/visual-spec.md`）。

### 2.2 🟡 / 💭 的典型形态

* 🟡：同构实现出现第三份副本（应收敛，参考 #372 的做法）；缺边界用例（空集、首窗、跨平台、LOF 一码多市场）；文档未随代码更新（这类**没有 CI 守门**，是文档漂移的唯一防线）。
* 💭：命名、注释措辞、不影响行为的简化。

## 3. 审查清单

### 3.1 通用五问（每个 PR 必答）

> 五问与第 0 节的五类缺陷一一对应。**逐问给结论，不适用要写「不适用」，不允许跳过。**

#### Q1 失败时会怎样？（对应「静默失败」）

本项目第一号问题，逐条穷举：

* 异常是抛出还是被吞？被吞了有没有日志 + 可检索记录（参考 #422 的 savepoint 隔离与 `SESSION_ABORTED`）？
* 循环里的单条失败是**隔离**还是**毒化 session**（#419：连接级 savepoint 无法隔离 ORM flush 失败）？
* 查询/分页有默认上限吗？会不会静默截断（#234 固定 `page_size=100`、#63 `--limit 30`）？
* 入参是被校验，还是被**静默覆盖/钳制**（#231/#236 `confirm_days`、#235 `nav_lag_days` 负值）？
* 测试里的 `skip` 是**真条件性**，还是在掩盖失败（#354/#371）？
* **判定**：存在「用户或运维无法感知的错误路径」= 🔴。

#### Q2 同类还有几处？（对应「同源漏网」）

* 改了 X，同构的 Y/Z 在哪？（#387 → #393、#249 → #349）
* **必须用 grep 或 AST 检索确认，不靠印象**——#382 的原始教训就是「以 grep 零残留验收，但结论从无机器保障且实际不成立」。
* **流程/规范类改动另有一条硬要求**：先检索全仓（含 `.qoder/`、`docs/`）确认**仓库里没有同主题的既存流程定义**，否则会产出两份并行规范。本文件首次合入前的审查正是栽在这一条：新标准与既存的 `.qoder/skills/issue-to-pr/` 给出**相反的动作指令**（审查者能否直接改作者的分支），而作者只检索了路径与 issue 号，没检索「是否已有既存规范」。**两份规范并存时，取舍取决于先读到哪个文件——正是 §0 要消灭的失效模式。**（该 skill 已因本条删除。）
* **判定**：未做同类排查 = 🟡；确知存在同类未修 = 🔴。

#### Q3 数值口径对吗？（对应「数值口径不一致」）

* 量化**只发生在产生点**（用户输入、确认计算、事件变动），读取与累加路径不量化；可用量闸门一律**先量化再精确比较**（无容差）。
* 走 `quantize` 统一入口，舍入模式与 §2.11 一致（#428 的教训：缺省舍入模式与文档声称的不符，静默错在 7 处）。
* 不要把 DECIMAL 经 `float()` 落库/落 JSON（#421）。
* `amount` 与 `actual_amount` 的含费语义（调仓买入 `amount = actual_amount − fee`；卖出金额为纯派生量）。
* **判定**：口径错误 = 🔴。

#### Q4 契约与文档要不要同步？（对应「文档-代码漂移」）

| 产物 | 触发条件 | 有无 CI 守门 |
| --- | --- | --- |
| `openapi.json` | 改 router / schema / 版本号 | ✅ `backend/check_openapi.py` |
| `ir-cli` response_fields | 改响应字段 | ✅ `gen_response_fields.py --check` |
| `business-constraints.md` 错误码 | 新增/删除 `BusinessError` code | ✅ `backend/tests/unit/test_error_codes_doc_sync.py`（#418 收口时建：在用码 ↔ 总表双向比对，含「码名写进散文里就算记过」的防堵；新增码漏登记会红） |
| 根 `AGENTS.md` / 模块 `AGENTS.md` / runbook | 改业务规则、流程、运维动作 | ❌ **无守门** |
| `visual-spec.md` | 改视觉口径 | ❌（但部分口径已有 ESLint 护栏） |

* **判定**：漏同步有守门的产物会被 CI 拦；**漏同步无守门的产物 = 🟡，且这是文档漂移的唯一防线，审查者必须主动问。**
* ⚠️ **有守门 ≠ 不会漂**：本文件自身即是反例——初版硬编码的 job 数与覆盖率阈值，在本文件合入前就双双失实（详见 §0 末注）。**大原则：文档里避免硬编码会漂移的数值与清单，改为指向源码。**

#### Q5 怎么回滚？

* 迁移可逆吗？不可逆是否按 #170 走 `SKIP_DOWNGRADE` 豁免并**约定合入后移除**（不可逆迁移的权威清单见 `docs/runbooks/deploy-rollback.md` 的回滚表，本文不维护副本）？
* 对生产存量数据的写操作是否幂等？是否需要先在备份/快照上演练？
* 部署影响是否写进 PR「部署影响」节（新依赖 / 配置变更 / DB 迁移）？

### 3.2 按改动类型追加的清单

| 改动区域 | 追加审查点 |
| --- | --- |
| `app/services/**` | 事务边界（不 `commit`、可 `flush`；自持 `SessionLocal` 的后台执行体与 `task_runner` checkpoint 属合法例外）；只抛 `BusinessError`；金额/份额先量化再比较；`skip_available_check` 仅限 auto_confirm 路径 |
| `snapshot_service.py` | 三表固定生成顺序（position → value → holding）；连续原则；级联回退日期键（申赎 `apply_date`、事件 `entitlement_date`、**交易不级联**）；重算为单一事务；取价只由 `nav_lag_days` 决定、禁止向前回退；**改本文件必须连带 `-k snapshot` 兜底测试** |
| `position_service.py` | 可用现金两条口径（`calculate_available_cash` / `compute_cash_balance`）不被混用；现金行判定用 `cash_amount IS NOT NULL`；现金重估只走 `manual_market_value` 覆盖层 |
| `trade_service.py` | `sync_transfer_group` 是配对腿同步的单一实现（不传播 `confirm_date`）；`trade.transfer_group` NOT NULL |
| `app/routers/**` | 保持薄适配（无业务分支、无 `try/except` 业务分支）；`db.commit()` 归属正确 |
| `app/models/**` + `alembic/**` | 迁移可逆 + 双方言 + 种子类 DML 幂等；`create_all → upgrade head` 顺序；外键删除行为维持 RESTRICT |
| 前端 `components/shared/*Content.tsx` | **表格/图表列结构改动必须目检**（`scripts/visual-verify.sh`）——E2E 断言定位与文本、不断言像素，列宽挤压与 CJK 竖排只有人眼看图能拦（#355 即 issue 里人眼发现、e2e 全程绿灯） |
| 前端双端改动 | `variant` 一般只改栅格列数/筛选栏折叠/控件宽度，故桌面断言多能 1:1 移植；**移动端路由是否存在以 `src/app/m/` 为准，不靠印象**（#371）；合法端专属 skip 只有两类：功能确实缺、输入设备语义缺 |
| 前端数值/色彩 | `format*` 系函数（禁止组件内 `toFixed`）；份额用 `formatSharesUnit`；空值占位 `--`；红绿仅用于盈亏 |
| `frontend/e2e/**` | 定位器走 `data-testid`（已有 ESLint 守门）；`skip` 合法性；选择框交互一律走 `e2e/helpers.ts` 不复制定位器（#372）；**禁止对 `E2E_ACTIVE` 跑 recalculate/catch-up/generate-next**；纯测试重构（pass/skip 形态应不变）由 CI `e2e-compare` 系 job 自动做归一化 diff 兜底，**形态变化属预期时才打 `e2e-morph-expected` 标签豁免**——打标签前先确认变化真是预期的 |
| 依赖变更 | `backend/requirements.txt` 是镜像与 CI 的唯一安装来源（`pyproject.toml` 的 `dependencies` 不参与构建）；**传递依赖不显式 pin 就等于没 pin**（#314：多数传递依赖仍浮动，清单以该 issue 与 `requirements.txt` 为准） |
| 脚本/工具（`scripts/**`） | 退出码是否反映失败（#409：参数错误返回 0 使调用方无法判定）；失败/中断路径是否恢复现场（#398 分支恢复）；**「从未产出过结论」类缺陷**（#402：内嵌 normalizer 崩了却一直没人发现，因为没人校验产物——现由 `scripts/tests/test_e2e_normalize.py` 锁定 JSON reporter 形态假设）；**工具链升级后先跑其单测**（Playwright 升级 → 该测试即 #402 的机器化防线）；新增脚本是否纳入 `scripts-test` job 或既有单测 |

### 3.3 涉及业务不变量的改动

此类改动一律先读根 `AGENTS.md` §2 与 `docs/reference/business-constraints.md` 再审查，本文不重复规则本体。审查时的判定要点：

* 改动是否**证伪**了某条已声明的不变量？若规则本身要变，是否同时更新了 `AGENTS.md` / `business-constraints.md`？
* 涉及「提前一天生效」类陷阱（如 `auto_confirm_after_snapshot(D)` 会确认 `ex_date == 下一交易日(D)` 的事件）时，作者是否读过 `backend/AGENTS.md` §1.3，而不是凭根文档概述推测？
* 数值口径、日期键、状态机迁移属于**最高危区域**：宁可要求补测试，不要相信「看起来对」。

## 4. 流程

### 4.1 角色与职责

| 角色 | 由谁承担 | 职责 |
| --- | --- | --- |
| 作者 | 人 + AI 协作 | L0 自审；按模板填 PR；响应审查意见；一切修复由作者执行 |
| 审查者 | 以 AI 审查为主，人做终裁 | 执行 L2 语义审查；给出分级结论；决定 🟡 是当场修还是开 follow-up |
| CI | 自动 | L1 机械门禁；`CI OK` 是 main 唯一 required check |

### 4.2 提交前自审（作者，必做）

1. **读自己的完整 diff 原文**——不是只看 AI 生成的改动摘要。AI 的总结会掩盖它自己没做到的事，这是自审存在的根本理由。
2. 跑**影响面**测试（圈定程序见 `backend/AGENTS.md` §2 表格；影响面拿不准宁宽勿窄）。
3. 前端跑 `scripts/verify-frontend.sh`（与 CI 同口径）。
4. 逐条回答通用五问，把结论写进 PR 自审清单。

### 4.3 提交 PR

* 使用 `.github/PULL_REQUEST_TEMPLATE.md`，四节（改动内容 / 关联 issue / 测试验证 / 部署影响）+ 自审清单全部落实。
* 规模护栏见 §5。
* ⚠️ **改 PR base 不触发 CI**（#377）：`on: pull_request` 只订阅 opened/synchronize/reopened，retarget 后 checks 为空，required check `CI OK` 永远无法满足——须 close/reopen PR 或推新 commit 重新触发。

### 4.4 审查

* **覆盖范围：全量 diff，逐文件。** 不因「文件多」而抽样——抽样正是小问题漏过的主因。
* 审查顺序：先看**意图自洽**（PR 描述 / 关联 issue 与 diff 是否说同一件事）→ 再逐条走通用五问 → 再按 §3.2 表格追加。
* 产出格式见 §6。**一次给完整反馈**，不要多轮挤牙膏。
* 不明确的意图**提问**，不要假设它错。

### 4.5 处置规则（关键）

| 级别 | 处置 | 是否阻断 |
| --- | --- | --- |
| 🔴 | **必须修复后重新审查**。不得以「后续 issue」方式绕过 | 阻断合入 |
| 🟡 | 当场修，或按铁律开 follow-up issue 后合入 | 不阻断 |
| 💭 | 记 issue 或忽略，但需在评论中明示取舍 | 不阻断 |

**与铁律的协调**（根 `AGENTS.md` §3.5 第 2 条「排查/审查中发现的问题只提 issue，不直接改代码」）：

* **审查者不得直接改作者的分支**——即便发现 🔴 也走「打回作者修」。理由不只是流程洁癖：AI 改 AI 写的代码会失去作者对改动的认知，且「AI 修改无第二人验证」等于取消了审查本身。
* **唯一例外**：纯机械修（错别字、格式化、注释笔误）且作者在评论中明确授权。

**follow-up issue 规范**：标题沿用现有惯例带 `（PR #X 评审 follow-up）`（如 #372 / #383 / #399 / #400），正文引用原评论并说明触发条件与验收标准。

### 4.6 合入

* **合入是人工关卡**：`CI OK` 与 L2 审查均通过后，仍**须用户明确确认才可执行合入**——合入即触发 CD、直接动生产，AI 不得自行合入。
* `CI OK` 必须绿（`skipped` 视为通过，为将来 `paths-ignore` 预留——见 `ci.yml` 汇总 job）。
* 合入 `main` **即触发 CD 自动部署**，因此「部署影响」节与上线冒烟不是形式主义。
* 上线冒烟按 PR 模板清单执行（health check + `ir portfolio list` + 关键数据抽查），**在合入之后**。

### 4.7 复盘（闭环，本机制的进化入口）

每 10 个 PR 或每月一次，把审查意见**归类统计**：

* 同一类意见重复出现 ≥3 次 → **评估能否下沉为 L1 门禁**（ESLint AST selector / CI 检查 / 契约守门脚本）。本仓库已有成功先例（#127 色板、#249 数值、#382 定位器）。
* 无法机械化的 → 补进本文 §3 清单，让下一个审查者无需重新发现。
* 判定为「作者认知盲区」的 → 补进模块 `AGENTS.md` 对应章节。

**这样做的意义**：L2 的产出不是一次性的评论，而是让 L1 水位持续抬高，把重复劳动从「每次审查都提」变成「机器永远拦住」。

## 5. PR 规模护栏

* **建议上限：单 PR ≤ 15 个文件且 ≤ 800 行净变更。** 超过时需在 PR 描述中说明理由或拆分。
* 现状参考（截至 2026-09-11 抽样，非长期指标）：近 40 个已合 PR 平均 7.5 文件 / 590 行净变更，最大 40 文件 / 1769+（#435 全库字符集统一属结构性批量改动，属豁免类型）。
* **拆分原则**：按「可独立验证的单元」拆，不按文件类型拆——拆成「后端一半 + 前端一半」会让两半都无法单独验证。
* **豁免类型**：机械批量改动（重命名、格式化、常量/函数收敛）、依赖升级、发布 PR（`release/*`）。

> 依据：审查注意力是有限资源，PR 越大，单位改动的审查深度越低，§3.1 五问越容易被跳过。

## 6. 审查产出格式

### 6.1 逐条评论

```
🔴 静默失败：单条失败被吞，运维无法感知
位置：backend/app/services/snapshot_service.py:412
为什么：except 内只 pass，无日志。该路径下 auto_confirm 失败会整体消失，
        与 #305 报告的可观测性缺口同源。
建议：改为记 logger.warning 并写入 warnings 列表（参考 #422 的连接级 savepoint 隔离写法）。
```

要求：

* **位置必须具体到文件:行号**，不接受「某处」。
* **必须解释为什么**，不只是「改成 X」。
* **建议用「建议」语气**（「考虑…，因为…」），不是命令。
* **必须写「做得好的地方」**——收敛到 helper、补齐了缺失断言、把静默改成显式报错，都值得点名。审查的作用是教，不是把关。

### 6.2 结论行（每次审查必须有）

```
审查结论：🔴 1 项 / 🟡 3 项 / 💭 2 项
建议：打回修改（🔴 修复后重新审查）
```

可选结论：`开 follow-up issue 后合入` / `可直接合入`。
