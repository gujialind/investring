# 代码审查标准与流程

> 本文是 InvestRing 的审查决策协议：明确审查对象，核实行为与证据，给出可复核的结论，再按授权处置。
> 开发动作与权限以[根指南](../../AGENTS.md#ai-agent-rules)为准，业务意图以[业务规则](business-constraints.md)为准，文档维护遵循[AI 文档规范](documentation.md)；本文不复制开发手册、完整业务规则或 CI 清单。

阅读路径：[职责与边界](#review-boundaries) → [审查输入](#review-inputs) → [通用五问](#review-questions) → [按风险加载](#review-risks) → [判定与处置](#review-disposition) → [输出与复核](#review-output)。

<a id="review-boundaries"></a>
## 1. 职责与边界

审查的价值是发现「检查全绿，行为仍错」，不是重复机器输出，也不是借机扩大开发范围。

| 层 | 执行者 | 负责什么 | 不能替代什么 |
| --- | --- | --- | --- |
| **L0 自审** | 作者（人 + AI） | 理解目标、读完整 diff、验证影响面、说明证据与取舍 | 独立 L2 审查 |
| **L1 机械门禁** | CI | 执行已编码的检查、测试和契约规则，提供可复核结果 | 作者的本地验证；未编码的意图与检查范围外的行为 |
| **L2 语义审查** | 独立审查者（人或 AI） | 核对意图、行为、失败路径、影响面和测试有效性 | 作者修复；用户授权与终裁 |

- **不重复机械诊断，不放弃语义判断**：单独复述 lint、类型或 CI 失败不是 L2 发现，列入验证状态即可；门禁范围遗漏、断言失效、例外扩大则须审查。可为疑点运行最小复现，不要求无差别重跑整套 CI；L1 与 L2 可以并行。
- **开发自检与独立审查分开**：作者在已授权开发范围内负责修复闭环；独立审查者即使发现 Blocker 也不直接改作者分支，避免作者失去改动认知、修改者自行宣告审查通过。作者调用 AI 自检不等于完成独立 L2。
- **审查代修唯一例外**：纯机械修（错别字、格式化、注释笔误），且作者在评论中明确授权；业务行为、测试断言、规则和豁免变更不属于机械修。
- **审查请求不附带远程写权限**：提 issue、发布评论/审查、打摘标签、推送、合入及生产操作均须相应授权；未授权时在当前会话交付结果。只操作已确认归属的本地验证环境，不动其他 worktree 的进程或数据。

<a id="review-inputs"></a>
## 2. 审查输入

开始前固定以下输入，缺项先查代码、测试、PR/issue 和项目约定；只有无法据此解决的关键歧义才询问。部分受阻时继续可独立完成的审查，不因材料未齐就假设实现错误。

| 输入 | 必须明确 |
| --- | --- |
| **目标与验收条件** | 要改变什么行为、什么必须保持不变、哪些范围不在本次任务内；PR 描述、关联 issue 与 diff 是否一致 |
| **比较基线** | PR 的 base/head SHA 与比较范围；本地审查说明 staged/unstaged/未跟踪文件或指定提交范围，不能只看最新 commit |
| **完整改动范围** | 增删改、测试、生成产物、文档和配置；沿调用方与消费者补足上下文，不以摘要代替原文 |
| **作者验证证据** | 本地影响面命令与结果、必要的双端操作/目检、CI 证据来源；不适用、未运行、无法验证分别说明 |

作者使用 [PR 模板](../../.github/PULL_REQUEST_TEMPLATE.md)交付上述信息及五问结论；自审与本地验证遵循[根指南任务入口](../../AGENTS.md#2-按任务加载)及模块指南，CI 不能代替本地验证，验证不了不提交。编辑时保留原行尾，不混入他人工作或无关重写。

**范围与规模**：全量逐文件审查，可分工但须汇总覆盖范围；工具截断、未读文件必须补齐，不能抽样后宣称全量。按共同目标、共同验收与可独立回滚的行为单元组织 PR，不要求一 issue 一 PR，不为凑行数合并无关改动，也不设每日 PR 配额（#608）。建议单 PR ≤15 个文件、≤800 行变更（新增 + 删除），这是软规模建议而非目标或硬门禁，超出时说明理由或按行为单元拆分；契约、测试和必要文档跟随行为，不拆成前后端各一半。机械批量修改、依赖升级和发布 PR 可说明规模豁免理由，但不豁免审查、验证或授权，也不因超限自动判 Blocker。

<a id="review-questions"></a>
## 3. 通用五问

按以下顺序核对，每问给**短结论 + 关键证据**；不适用须说明理由，一个证据可支撑多问。五问不是五类缺陷配额，不要求为了填满报告制造发现；涉及的专项规则从[风险清单](#review-risks)加载。

<a id="review-behavior"></a>
### Q1 行为符合意图与业务不变量吗？

- 从真实入口沿数据流核对输入、状态变化和可观察结果：是否满足验收条件，原本不该改变的行为是否保持？不要只看局部函数“写得对”。
- **涉及财务必须显式核对**金额、份额、净值的量纲与含费语义，双层账本、现金/在途边界、日期键和状态机；按[业务规则](business-constraints.md)确认，不以数值接近或字段同名推定等价。
- 对照[量化产生点](business-constraints.md#rule-precision)：helper、舍入与中间量是否正确，可用量是否先量化再精确比较，读取/累加是否被额外量化；财务落库与[审计载荷](logging.md#logging-audit)不能经 `float()` 丢失 Decimal 精度/标度（#428 / #421）。
- 缺省、未提供、null、零值与空集是否按约定区分，是否静默覆盖输入？预览/确认、创建/更新是否在应相同处使用相同规则？
- 文档意图与实现冲突时列出双方证据并询问，仅暂停相关判断；不能默默改规范迎合实现。业务规则确要改变时须有明确决策并同步正文与验证。

<a id="review-failure"></a>
### Q2 失败是否可见，状态是否安全？

- 沿「入口 → service → DB/外部依赖 → 响应或任务记录」追踪业务拒绝、异常和部分成功；检查调用方实际如何消费，而非只看 `except` 有没有日志。
- 实际失败是否到达用户或运维可感知的出口？`200 + errors` 不能被当完整成功，后台任务须有可检索终态或告警；按[日志规范](logging.md)核对，不要求各层重复记录同一异常（#305）。
- 单条失败是否正确隔离、留下半成品或毒化 session？不可恢复时是否停止继续写入？事务与 checkpoint 的不同保证见[事务专项](#review-transactions)。
- 超时、重试、重复提交、并发与中断是否会重复记账、覆盖更新或误报成功？仅核对本次真实入口，不凭空要求新的重试/锁框架。
- 分页、批处理和降级是否将不完整结果冒充全集，默认上限或失败条目是否对消费方可见（#234）？

<a id="review-impact"></a>
### Q3 同类入口、消费者与契约是否同步？

- 用 grep/AST 检索同构入口与调用方：同服务分支、预览/确认、创建/更新、桌面/移动、API/CLI；记录**范围、模式、命中位置和处置结论**，无命中也说明查了哪里。一次关键词零命中不能证明全仓无同类问题（#387 → #393、#382）。
- 检查字段含义、默认值、null、状态码、分页和部分成功语义如何影响消费者；生成契约一致不等于前端/CLI 已正确适配，相关入口见[契约专项](#review-contracts)。
- 按[文档同步条件](documentation.md#doc-sync)说明已同步的正文、引用和生成产物，或无需同步的理由；生成产物由生成器更新，不能手修来掩盖上游差异。版本、阈值和 job/文件清单引用源码，不另存易漂移副本。
- **流程/规范变更**还须检索根/模块 AGENTS、`docs/`、`.github/`，并定向核对当前项目及用户 AI 工具目录的 rules/skills/agents（如 `.qoder/`、`.codebuddy/`、`.trae/`）；不扫描无关会话、凭证、缓存或其他 worktree，不可访问的范围如实写明。
- 仓库同主题规则只保留一份有效正文，本地工具作薄适配；其评分、自动修复指令不能放宽项目标准或授权。冲突须指出，不擅改私有配置或纳入版本控制（曾与本地 `issue-to-pr` 流程冲突）；任务外既存问题按[处置规则](#review-disposition)单列。

<a id="review-evidence"></a>
### Q4 哪些证据证明改动有效并覆盖回归风险？

- **验证行为，而非实现自证**：bug 修复须有能区分修复前后的用例或最小复现；关键规则须有应被拒绝的反例，不能只证明“跑到这一行”。mock 不得替换掉正在验证的业务判断。
- **追踪原有保护**：删除/替换的断言在哪里继续生效，或为何已不适用？skip 是否真有条件，是否用选择器失败、种子退化或“移动端大概没页面”掩盖错误？这类“覆盖无声蒸发”即使 CI 绿也必须核对（#354 / #371 / #382）。
- **对齐影响面与证据范围**：核心服务改动连带快照兜底；交互需实际操作与影响面 E2E，表格/图表列结构需双端有代表性数据的目检。用例存在、截图为空或测试旧版本都不能证明本次行为。
- **看见覆盖分母**：后端覆盖率主要约束 `app`，前端主要约束 lib 纯逻辑；components/hooks/stores、迁移等不能凭绿灯推定已有单测。精确范围见模块指南与配置，检查本次是否收窄分母或新增未收集路径。
- **证据必须可追溯**：区分作者提供、CI 产出和审查者实跑，注明版本、范围、结果及未验证项；疑点可以用最小复现补证据，但不能把未运行写成通过。证据不足按[完成状态](#review-status)处理，不靠发现数或覆盖率高低宣布无缺陷。

<a id="review-recovery"></a>
### Q5 上线与回滚能否保护存量数据？

- 说明新依赖、配置、schema 和存量数据影响；无部署影响也给理由。PR「部署影响」应写成功判据、恢复前提及必要的演练证据，不只写“可回滚”。
- 区分代码回退、数据库回退与数据恢复：旧镜像能否读写新 schema，已发生的写入能否恢复，是否需要备份/前滚？downgrade 存在不等于无损，具体例外见[迁移专项](#review-transactions)。
- 存量数据变更是否幂等，中断后的重跑是否会重复处理，是否需要先在隔离备份上演练？审查不授予生产或真实投资数据写权限。
- 确认是否实际触发部署、何时执行上线冒烟；文档改动的 CI/CD 例外不等于免审查或免授权，见[合入条件](#review-merge)。

<a id="review-risks"></a>
## 4. 按风险加载的专项清单

仅加载本次涉及的项，多类型取并集。以下保留容易遗漏的保护、例外和验证入口，完整定义归链接正文；不要将关键词命中直接当违规。

<a id="review-financial"></a>
### 4.1 财务计算与生命周期

- [双层账本](business-constraints.md#rule-ledger)、[生命周期](business-constraints.md#rule-lifecycle)、[交易日](business-constraints.md#rule-trading-day)：核对首窗、跨平台、LOF 一码多市场、确认/回退与部分失败；自然日不能替代交易日。
- [快照](business-constraints.md#rule-snapshot)与[后端核心服务](../../backend/AGENTS.md#13-核心服务)：三表生成顺序、严格连续/取价、重算原子性、级联日期键以及**交易不级联**；下一交易日生效不能套当天规则。可用现金与全量余额不可混用，现金行按 `cash_amount IS NOT NULL`，现金重估只走覆盖层。
- [调仓](business-constraints.md#rule-trade)及相关领域：配对腿同步单点、不传播 confirm_date、组号非空；预览只读且与确认同口径，可用量豁免仅适用已声明的自动确认路径。
- [量化守卫](../../backend/tests/unit/test_quantize.py) `TestFinancialQuantizationGuard`（#590）只覆盖登记的核心模块与明确读侧豁免，不证明所有产生点正确；仍需舍入模式、两步量化和临界比较反例。按[后端影响面表](../../backend/AGENTS.md#2-跑测试)验证，核心服务改动连带 snapshot 兜底。

<a id="review-transactions"></a>
### 4.2 事务与数据库迁移

- [分层与 session 所有权](../../backend/AGENTS.md#11-分层目录与职责)：普通 service 不 commit/rollback 调用方注入的会话，只抛领域异常、不依赖 HTTPException，router 保持薄适配；自持 `SessionLocal` 的后台执行体与 `task_runner` checkpoint 是明确例外，不能按目录一刀切。动态事务测试不能证明所有新入口均合规。
- [自动确认](../../backend/AGENTS.md#backend-auto-confirm)的 ORM flush 失败靠 **session 级 savepoint** 隔离；[审计 Core INSERT](logging.md#logging-audit)的连接级方案不能套用（#419）。不可恢复会话须终止后续操作并保留根因，任务终态/部分成功遵循[任务记录规范](logging.md#logging-tasks)。
- [迁移约定](../../backend/AGENTS.md#5-迁移alembic)与[回滚表](../runbooks/deploy-rollback.md#43-现有迁移可逆性速查downgrade-风险)：验证新旧库起始态、双方言适用性、DML 幂等、外键 RESTRICT 与约束名，以及 `create_all → alembic upgrade head` 顺序。CI 只对**最新一条迁移**做 MySQL 降升，双方言 pytest 不证明全历史或生产存量均可回退。
- 采纳型 no-op、含特定数据时条件跳过、不可逆需备份/前滚，是不同情形，不能为形式可逆销毁数据。确需 `SKIP_DOWNGRADE` 豁免时沿用 #170，写明恢复方案与合入后回收安排；main 守卫会拒绝残留，不是永久免责。

<a id="review-frontend"></a>
### 4.3 前端交互、展示与 E2E

- [共享组件与预览](../../frontend/AGENTS.md#12-组件复用)：确认弹窗走 preview，query key 包含影响结果的输入，加载/失败时禁止提交；重开、切换对象、修改输入不能用旧缓存确认。移动端路由存在性以 `src/app/m/` 为准，不凭印象 skip。
- [视觉规范](../design/visual-spec.md)：数值走 `format*`、份额走 `formatSharesUnit`、空值用 `--`、红绿仅用于盈亏；共享表格/图表列结构改动须用 `scripts/visual-verify.sh` 双端目检有代表性数据（#355），空表截图不能证明列宽、换行和结对布局正确。
- [E2E 约定](../../frontend/AGENTS.md#4-e2eplaywright)：定位器契约与选择框/浮层 helper、真实双端覆盖、合法 skip、种子和重试隔离；**禁止对共享 `E2E_ACTIVE` 跑 recalculate/catch-up/generate-next**，推进场景自建隔离组合。运行前确认服务、端口和数据归属，不能测到其他 worktree 或旧版本。

<a id="review-contracts"></a>
### 4.4 安全、公开契约与 CLI

- 涉及鉴权、输入输出或数据访问时，核对登录态、角色与资源边界，以及注入/越权路径；UI 隐藏按钮不能代替服务端校验，响应、日志和错误信息不得泄露密码、Token 或不应暴露的数据。
- router/schema/版本变化用 [check_openapi.py](../../backend/check_openapi.py)核对，响应字段用 [gen_response_fields.py](../../ir-cli/scripts/gen_response_fields.py)生成同步；L2 仍须核对默认值、null、状态码及消费者行为。[CLI 指南](../../ir-cli/AGENTS.md#3-契约语义)中的摘要/机读字段、分页与部分失败须与实际输出和退出码一致。
- [错误码守门](../../backend/tests/unit/test_error_codes_doc_sync.py)覆盖码集合双向同步与已有稳定符号锚点有效性（#418 / #521），**已有码新增抛出点是否全量登记没有反向守门**，须人工核对本次影响面（`known_gap`，#583）。[文档检查器](../../scripts/check_context_docs.py)只查受管入口、链接、锚点和旧引用，不能证明语义同步或全仓无遗漏。

<a id="review-guards"></a>
### 4.5 测试设施、CI 与工具链

- 门禁变更要审扫描范围、空集合、路径映射、退出码、`continue-on-error`、结果聚合及例外回收，并补能让错误规则失败的反例；不能同时放宽规则与测试后用绿灯自证（#490 / #509 / #590）。`CI OK` 是 job 结果核验，不证明内部每一步都执行，也不是抵御同时篡改策略与测试的安全边界。
- 纯测试重构应保持 E2E pass/skip 形态；[形态对比](../../frontend/AGENTS.md#e2e-归一化对比纯测试重构验证)两侧应用均为 PR head，只替换 E2E 目录，不能据此证明应用无回归。预期形态变化经核实并授权后才用 `e2e-morph-expected`，写明原因并回收；标签巡检只报警变红，不自动摘标，也不是 required check（#410 / #483）。
- 脚本参数错误、失败、中断及产物缺失不能假成功，恢复现场时只处理归属明确的对象；测试库不能凭名字含 test 就清理，遵循[测试库隔离约定](../../backend/AGENTS.md#2-跑测试)。新增脚本纳入 `scripts/tests/`，验证失败出口与产物而非只看命令启动。
- 后端镜像安装来源是 `backend/requirements.txt`，仅改 `pyproject.toml` 不改变安装结果，未钉传递依赖不能声称可复现（#314）。工具链升级后先跑适配单测：Playwright 升级须跑 `scripts/tests/test_e2e_normalize.py` 验证 reporter 形态假设（#402），Vitest 联动升级遵循[前端指南](../../frontend/AGENTS.md#3-单元测试vitestissue-253)。

## 5. 判定与处置

<a id="review-disposition"></a>
### 5.1 缺陷严重度与处置

先核实触发条件、行为、已有守卫和合法例外，再按**实际影响**定级；CI 能否发现不决定严重度，工具分数和个人偏好不能代替证据。同一根因合并列出位置，不按命中行数重复计数。

| 级别 | 判定依据 | 处置 |
| --- | --- | --- |
| **Blocker** | 已证实破坏正确性、安全性、数据完整性、公开契约或明确保护边界 | 作者修复并重新审查，未解除不得合入；不得用 follow-up 绕过。被证据证伪时记录撤回理由 |
| **Suggestion** | 有具体维护或验证收益，但未发现会破坏上述保证的问题 | 可选改进，不阻塞审查结束：可修复并验证，或接受现状、不做、暂缓并记短理由；确需跟进时经授权登记。未决定则如实列为可选建议，不强制修复或建 issue，不假称用户已接受（#608） |
| **Nit** | 不影响行为的命名、措辞、可选简化 | 明示可选，记录已有取舍；未决定同样不阻塞，不反复追问，不为每条自动建 issue |

- 静默错误/假成功、财务或日期状态错误、越过 session/数据边界、鉴权/契约破坏、危险迁移无恢复安排、保护性覆盖被实质移除，都按 Blocker 判据核实；前端违反明确数值/单位/色彩规则不能当个人风格略过。
- 不因第三份副本就要求抽象；不因删了测试就定罪，须看原保护是否仍在。文档也按影响定级：一般说明遗漏是 Suggestion，错误运维步骤会造成数据损失则是 Blocker。
- **任务外既存问题单列**，说明不是本次引入，先核实再经授权跟进；不能因发现旧问题无限扩围。若其使本次目标或验收无法成立，说明关联并请用户决定扩围，不以“既存”掩盖本次依赖的错误。
- 同一未合入 PR 范围内的修正直接追加改动，不另开 issue/PR；延期且确需追踪的事项按[Issue 约定](../../AGENTS.md#32-issue-约定)登记，不把无关工作硬拼进下一 issue。确需新建 follow-up 时遵循 issue 模板：源自 PR 的标题带 `（PR #X 评审 follow-up）`（如 #372），其他来源如实注明；正文引用原评论或会话结论，说明证据、影响、触发条件与验收标准。修复角色与操作授权仍受[职责边界](#review-boundaries)约束。

<a id="review-status"></a>
### 5.2 审查完成状态

**严重度回答“问题有多严重”，状态回答“能否结束本轮审查”**；证据不足不是第四种严重度，零条发现也不自动通过。

| 状态 | 使用条件与下一步 |
| --- | --- |
| **审查未完成** | 范围未读完、关键测试/目检缺证据或关键疑点待确认；列缺口并补证据，继续可独立完成的部分 |
| **打回修改** | 已证实的 Blocker 未解除；列明修复与复核要求，其他未完成项仍须披露 |
| **通过，可进入合入确认** | 全量审查完成、关键证据充分、无未解除的 Blocker；可选建议如实列出即可，不要求逐条修复或登记，仍须满足下方合入条件 |

缺影响面测试或迁移验证先作为验收证据缺口，不能写成已证实的行为错误；若另有行为错误或保护被撤掉，按对应严重度报告。无法运行验证不等于失败，也不等于通过；L2 完成时 CI 可仍在运行，须单独写明其状态，不建议立即合入。

<a id="review-merge"></a>
### 5.3 合入条件

- **三个条件缺一不可**：目标版本 `CI OK` 绿、L2 通过、用户明确授权本次合入；纯文档也不免授权。“审查通过”只表示可以请求合入确认，不是操作许可，不能使用旧版本结论或部分 job 绿替代。
- **L2 由维护者发起**（含其授权的 AI 执行），结论按 §6.1 字段模板以 **PR 评论**留痕，PR 正文不承载审查结论（#633，修订 #560/#615 的正文留痕门禁，CI 不再检查正文结论行）；作者的 L0 自审与验证证据仍经 PR 模板交付，作者自检不等于独立 L2（§1）。
- [ci_gate.py](../../scripts/ci_gate.py)按事件与 Git 变更独立重算（#587）：必需 job 只能 success，明确不适用才允许 skipped；failure/cancelled、缺结果或解析/基线错误均不通过。PR 按[路径策略](../../scripts/ci_policy.json)选择，触碰的栈仍全量，未知路径/门禁变化保守验证，文档路径不等于全部跳过。
- **PR 触发器禁止 `paths-ignore`**（#456），否则 required check 可能永远不产出；改 base 也不触发当前 CI（未订阅 `edited`，#377），须经授权 close/reopen 或推新 commit 触发，不能空等。
- main push 被文档过滤规则排除时不产生 CI run、不触发 CD、不推进部署标签；未过滤则保守全栈验证，通过后自动部署，E2E 形态对比仍仅适用 PR。具体模式以 [workflow](../../.github/workflows/ci.yml)为准（#456 / #462；跨栈与时间流逝型失效取舍见 #482）。
- 仅在实际部署后按模板做 health check、`ir portfolio list` 与关键数据抽查；无部署注明不适用，不提前勾选，生产操作仍须授权。

<a id="review-output"></a>
## 6. 输出与复核

### 6.1 发现与结论

完成本轮范围后集中给出反馈，按严重度排列，不用低价值 Nit 淹没关键问题；这不意味着后续新证据不能产生新发现。每条须给**级别、位置、触发条件、证据、影响与建议**，不能只说“改成 X”。

先用白话说明“会错什么、是否需要现在处理、推荐的最小做法”，再给技术依据；区分已复现、代码分析推断与尚未验证，术语就地解释。不把“检查无法执行”说成“检查发现不一致”，不只丢符号或事故编号让维护者裁决。可选项说明不做的代价，维护者表示不理解不等于同意增加工作。新增机制或额外任务的建议简要比较更小的替代方案和维护负担，自动检查的取舍见[按需保护](#review-guard-cost)；不新增必填长表，不编造发生概率、耗时或节省数字。

```text
[级别] 用白话说明问题
影响与建议：谁会得到什么错误结果，是否急需处理；推荐的最小做法，可选项不做的代价
位置：本次审查版本的 文件:行号 或最小行范围；必要时补调用点
触发与证据：什么输入/状态会进入该路径；实现、规则或复现如何证明问题，哪些尚未验证
验证：需要修改时说明如何确认修正有效
```

PR 审查的结论以 **PR 评论**发布，PR 正文与 PR 模板不复制本字段块（#633）。结论使用以下字段，可链接已有证据而不重复粘贴：

```text
审查对象：PR/本地范围；base/head 或当前差异标识
覆盖：已审范围；未审部分及原因（无则写无）
五问：Q1 行为…；Q2 失败…；Q3 同步…；Q4 验证…；Q5 恢复…（不适用须给理由）
证据：作者提供 / CI / 审查者实跑的版本、范围与结果；未验证项和剩余风险
发现：Blocker X 项 / Suggestion Y 项 / Nit Z 项
状态：审查未完成 / 打回修改 / 通过，可进入合入确认
待确认或任务外发现：证据、影响与所需决定；可选建议注明已有取舍或未决定，不阻塞（无则写无）
做得好的地方：具体做法与证据（无值得单列的内容可注明）
```

没有发现时写「在上述范围内未发现需报告的问题」，不宣称没有缺陷。不得把作者/CI 的结果写成自己实跑，也不把未经核实的工具输出直接当发现；报告不包含完整敏感日志、真实投资数据或模型内部推理。当前定位用行号，长期规则引用用稳定符号或锚点。

<a id="review-recheck"></a>
### 6.2 修后复核

作者提供修复说明与回归证据，审查者复核原问题、修复新增 diff 和影响面。head/base 或工作区内容变化后重新确认范围与相关验证，不沿用旧版通过结论；大幅变化重新全审。修复或撤回的发现记录结论及复核版本，未读完新增范围不得宣告本轮完成；可选建议接受现状、不做或暂缓时记短理由，未决定如实保留，不要求虚构修复版本或额外回归。

本轮范围审完、必修问题解除且关键证据充分后即可结束，不靠继续寻找可选改进延长审查；后来出现的真实严重问题仍须报告。

<a id="review-guard-cost"></a>
### 6.3 将重复发现转化为长期保护

按具体失效与实际影响评估，不设每月、每若干 PR 或重复次数触发的归类义务（#608）。新增自动检查前，先核实已有保护，比较修正问题源头、简化规则、补已有测试或不做的代价；没有新增保护收益，不默认再加一层。

确需增加时，简要说明能避免什么错误、已有检查为什么不够、适用范围及以后要维护什么。不要求先发生真实事故，但须有可复现或可由代码说明的失败场景；未核实的担忧先调查，不据此宣布阻塞。获准的守门仍须定义扫描边界、反例与例外回收，保留必要的正确性、安全检查和验证检查有效性的测试。

新增门禁、规范或后续任务仍需相应授权，不因一次审查自动执行；决策与长篇复盘留 issue，不为本原则新增评分表、定期审计或检查层。
