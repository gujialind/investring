# AI 文档规范

> 适用于 AI 对本仓库文档、规范入口和源码规范引用的读取、编写与迁移。本文约束文档工作，不授予提交、发布或修改生产环境的权限。

<a id="doc-ownership"></a>
## 文档职责与单一事实来源

| 载体 | 应保存的内容 | 不应保存的内容 |
| --- | --- | --- |
| 根 [AGENTS.md](../../AGENTS.md) | 项目地图、任务路由、跨域不变量摘要、动作边界 | 完整领域规则、长操作手册 |
| 各模块 AGENTS.md | 局部架构约束、验证入口、必要例外 | 已由专题持有的完整说明 |
| `docs/reference/` | 业务意图、规范正文、边界与设计理由 | 会话过程、临时实施计划 |
| `docs/design/` | 视觉/交互口径与验收判据（[visual-spec](../design/visual-spec.md) 持有） | 组件实现细节、临时设计稿、与 visual-spec 重复的业务规则 |
| `docs/runbooks/` | 操作前提、步骤、成功判据、失败恢复；一次性 how-to、排障流程（现象 → 诊断 → 恢复） | 与参考规范重复的业务公式 |
| `docs/reviews/` | 评审与度量复盘的批次存档（含明细数据），不进默认加载 | 业务规则正文；仍有效的条款归 `docs/reference/` |
| [CLI_MANUAL.md](../../ir-cli/CLI_MANUAL.md) | CLI 的用户操作、参数与示例 | 另一份后端业务规则 |
| 生成契约 | 生成器负责的接口事实 | 手工修补的生成内容 |
| CLAUDE / 工具规则 | 指向以上事实源的薄引用 | 按工具复制的独立规范 |

- 同一规则只能有一份有效的完整正文；其他位置保留短摘要和精确引用。
- 优先修改已有承载文件。确需新文档时，先确认没有同主题正文，再补入口，不创建孤立规范。
- 源码说明当前实现，规范表达已批准的业务意图。二者冲突时列明差异和证据，暂停相关语义修改并询问用户；不得默默改规范迎合缺陷，也不得仅凭文档擅改实现。
- 业务规则正文由 [business-constraints.md](business-constraints.md) 持有；日志、版本、审查分别由 [logging.md](logging.md)、[versioning.md](versioning.md)、[code-review.md](code-review.md) 持有。
- **目录登记（doc-ownership，#862 第 9 项）**：在 `docs/` 下新增子目录须同批登记——受管内容在职责表补行并挂入口；仅本地使用的临时区在 `.gitignore` 登记（先例：`previews/`、`plans/`、`handoffs/`、`evaluations/`）。不留未跟踪也未忽略的中间态。临时稿结论定稿后的回写优先级：**长期有效的规则结论进规范正文，issue 持决策过程**（不写成「或」；维护者第 4 项定案「硬化且只管被触碰的规则」）。
- **runbooks 命名与生命周期（#862 第 8 项）**：issue 号前缀 = 一次性 issue 驱动操作记录（如 `493-`）；带执行留痕的 runbook 头部须标生命周期状态（已执行 / 部分完成+豁免清单 / 长期有效），只陈述现状、不代维护者打勾。

<a id="doc-content"></a>
## 内容与表达

- 优先记录读代码不容易得到的意图、不变量、适用边界、取舍和例外。可直接查到的路由、字段、枚举、版本及文件清单引用源码，不再维护副本。
- 使用明确的“必须 / 禁止 / 建议”，写清适用对象；例外必须说明范围和理由，不能只写“特殊情况除外”。
- 历史事故只保留仍有效的约束、必要理由和原决策引用。调试过程和长篇复盘不进入每次会话默认加载的指南。
- 规则形态由 issue 决策塑造时，在首次陈述处标注首个决策号，后续改变形态的决策另行注明；源码可直接读出的事实不机械标号。
- 区分定义与实现细节、当前行为与计划、已验证与待验证。不能将建议写成已存在的能力。
- 示例只展示必要信息，优先引用现有实现及代表性测试；不得复制另一套财务公式或误用不同层的判据。
- 不为行数或 token 目标删掉业务例外、授权边界和关键原因，也不为凑行数添加空话。

<a id="doc-issue-spec"></a>
## 方案承载与开工复核（#929）

- **正文位置**：任务级 SPEC 默认放在 issue 正文的「评估结论 → 选定方案 / 实施方案（SPEC）」，记录范围、非目标、关键行为和接口约束；步骤与必要依赖归「待实现改动」，验收标准只维护在「验收断言」，不复制多套清单。长期规则仍由既有专题持有，issue 记录任务方案与决策过程；本机草稿不能作为跨设备接续的唯一入口。
- **当前状态**：需要跨设备接续或先定方案后实施时，在正文前部简记方案状态/版本、实施状态（如「方案 v1 已确认，实施待排期」）、批准记录、评估基线及开工条件；批准记录用可读取的链接，或经授权回填确认日期与范围。未确认则标草案，无明确排期不强制填日期，小 bug/chore 不套长表。
- **版本与历史**：正文持当前有效方案，讨论、批准与变更缘由可留评论，已采纳结论须回填正文并保留决策出处与关键取舍；待确认的改案与已确认版本分清，不以最新评论自动覆盖定稿。影响范围、行为或验收的实质变更更新方案版本与批准记录，不因排版修正机械升版。
- **开工复核**：待实施任务开工时，对照最新代码、规范及依赖复核关键假设；有实质变化才更新方案并重新确认，不因基线有无关提交就整轮重审。方案确认不等于实施或远程操作授权，仍遵循根指南的动作边界。
- **PR 承接**：实施既有方案的 PR 引用 issue 的实际方案版本并说明偏差；偏差按根指南回填 issue，PR 持本次实现范围与验证证据，不维护第二套完整 SPEC。长期有效的规则变化仍按[文档同步](#doc-sync)同批更新，不把待实施方案写成现有能力。

<a id="doc-images"></a>
## 截图与设计定稿（#929）

- **隐私与上传**：仅确认无真实投资数据、账号或其他敏感信息的种子/演示截图及纯合成设计图可作为公开 issue/PR 原生附件；公开附件无需认证即可访问。上传仍须相应授权，可网页粘贴，或使用支持 `--attach` 的 GitHub CLI，如 `gh issue comment <编号> --body "<说明>" --attach "<图片路径>"`；以当前设备帮助确认支持，不另建图片仓库或上传脚本。
- **真实数据**：确需保留的敏感截图仅放经确认的私有存储，公开 issue/PR 只留不泄密的引用；不得在公开链接中带令牌或可绕过鉴权的分享凭据。私有存储的建立、上传及接收工具权限须分别确认，不因可写工作区内路径就推定有权限。
- **验证证据**：bug 优先用 E2E 种子数据复现；保留关键截图并注明所测版本与场景，不长期归档全部临时截图。跨设备交付须确认接收工具能读取原图及目标设备能查看，分别记录已验证/未覆盖范围；仅有链接不等于读图成功，CI 临时产物不作长期判据的唯一载体。
- **设计判据**：issue 验收断言链接本次批准的具体图片版本及批准记录，注明页面、桌面/移动端和必要的主题/尺寸。文件名可带版本以便辨认，但不能代替定稿绑定；变更新发附件，保留旧版历史并更新当前指针，不将普通预览当定稿，也不将临时设计稿复制进 visual-spec。
- **历史与现行规则**：旧 issue 定稿只证明当时决定，不永久代表现行界面；不得仅凭旧图恢复已撤回的设计。新设计与规范的差异须明确批准并同步规范，未解释的冲突先询问；不要求后续改版重绘全部历史图，附件及关闭的 issue 均不是不可变存证。

<a id="doc-reading"></a>
## 按任务读取

1. 从根指南的任务加载表定位模块与专题，多类型任务取并集。
2. 先定位标题或符号，再读对应章节、实现及相关测试；信息不足才扩展范围。
3. CLI 先读命令索引，再读对应命令组；视觉相关任务才额外加载 visual-spec，非视觉任务仍读前端模块指南。
4. 不默认全文加载所有专题、CLI 手册、历史记录或其他 worktree；已委派的搜索不再重复执行。

<a id="doc-sync"></a>
## 何时同步

业务规则、公开契约、配置、运行前提、测试数据契约或操作流程变化时，必须同批更新：

- 持有规则的正文；
- 受影响的模块入口、源码注释及交叉引用；
- 对应生成产物与可执行验证。

PR 必须说明“已同步文档及位置”或“无需同步及理由”。不要求每个代码 PR 修改 Markdown；纯内部重构且外部约定不变时可说明无需同步。文档承诺必须有依据，不能用“已同步”替代检查。

<a id="doc-references"></a>
## 稳定引用

- 文档链接使用相对当前文件的仓库内路径；禁止将本机绝对路径或 `file:///` 地址写作共享入口。
- 长期跨文件规则引用使用显式稳定锚点（如 `rule-snapshot`）或稳定标题，不新增仅靠章节序号的引用；重命名或迁移时同批修复调用方。
- 受管文档内引用章节一律写作 `§N.M`（跨文件时写成 `路径 §N.M`，如 `docs/design/visual-spec.md §1.5`），该写法由[检查器](../../scripts/check_context_docs.py)校验编号在目标文件里真实存在——改标题号必须同批改引用，否则门禁判红。叙史谈旧状态（同句带 issue 号或「已过时」类词）的引用不校验。
- 源码引用以文件和符号定位。代码链接可指向文件，并注明 `文件::符号`；不要把源码行号当永久锚点。
- [错误码总表](business-constraints.md#错误码总表) 的标题、表结构及 `文件::符号` 格式是机器接口，不得随排版重构破坏。
- 该文档正文中，单独反引号包裹的大写下划线 token 被现有检查器视为错误码。非错误码常量应明确字段语境（例如 `market="CN_EXCHANGE"`），不要靠扩大豁免让检查变绿。

<a id="doc-migration"></a>
## 迁移与去重

1. 在任务记录中逐项确认旧规则的新落点，含理由、历史决策来源和例外；不另建永久迁移台账。
2. 合并到既有主题后删除旧完整正文，旧入口改为引用，不保留两份同时有效的说明。
3. 同批检索并修复模块指南、专题、runbook、模板和源码注释中的活动引用；本地工具薄适配也需核对，但不得擅改权限或将私有设置纳入版本控制。迁移后须另行检索全仓旧引用并逐项判定，受管清单检查通过不代表清单外无残留。
4. 发现冲突先报告，不能在“文档整理”中改业务行为、删除保护禁令或扩大本次授权。

<a id="doc-verification"></a>
## 验证与交付

- 核对完整 diff：规则无遗漏、引用可定位、例外未丢失、生成产物没有手改。
- 从仓库运行 `python scripts/check_context_docs.py`；自测为 `python -m pytest scripts/tests/test_context_docs.py scripts/tests/test_ci_path_mapping.py -q`。受管文档与源码引用文件明确列在[检查器](../../scripts/check_context_docs.py)的 `MANAGED_DOCS` / `SOURCE_REFERENCES`，不递归扩展目标、不访问外部网站，也不涵盖被忽略的本地工具规则；目前识别普通行内 Markdown 链接、引用式链接定义、显式 ID、ATX 标题与散文章节引用 `§N.M`，代码围栏中的示例不当作入口。
- CI 的 changes job 在 checkout 后无条件运行此检查，docs-only PR 也不绕过；自测复用 Run scripts tests。错误码总表及源码符号继续由已有后端测试守门，不复制 AST 逻辑。
- **受管集合扩表评估（doc-verification，#862 第 9 项）**：承载跨文件 `§N.M` 引用或被入口按路径引用的长期文档，**在新增受管内容登记时同批评估**是否纳入 `MANAGED_DOCS`；`docs/reviews/` 批次存档不进受管集合。不设独立定期巡检。
- 运行本次影响面的契约检查及相关测试；检查范围和局限必须明示。机械检查不能证明业务语义正确，仍需对照实现与测试核实。
- 分别报告通过、失败、未运行和无法验证，不能把计划执行写成执行完成，不能用 AI 自评代替证据。
- 不将凭证、真实投资数据、完整运行日志或会话转录写入文档。任务授权和临时例外不自动升级为永久权限或全项目规则。
