# AI 文档规范

> 适用于 AI 对本仓库文档、规范入口和源码规范引用的读取、编写与迁移。本文约束文档工作，不授予提交、发布或修改生产环境的权限。

<a id="doc-ownership"></a>
## 文档职责与单一事实来源

| 载体 | 应保存的内容 | 不应保存的内容 |
| --- | --- | --- |
| 根 [AGENTS.md](../../AGENTS.md) | 项目地图、任务路由、跨域不变量摘要、动作边界 | 完整领域规则、长操作手册 |
| 各模块 AGENTS.md | 局部架构约束、验证入口、必要例外 | 已由专题持有的完整说明 |
| `docs/reference/` | 业务意图、规范正文、边界与设计理由 | 会话过程、临时实施计划 |
| `docs/runbooks/` | 操作前提、步骤、成功判据、失败恢复 | 与参考规范重复的业务公式 |
| [CLI_MANUAL.md](../../ir-cli/CLI_MANUAL.md) | CLI 的用户操作、参数与示例 | 另一份后端业务规则 |
| 生成契约 | 生成器负责的接口事实 | 手工修补的生成内容 |
| CLAUDE / 工具规则 | 指向以上事实源的薄引用 | 按工具复制的独立规范 |

- 同一规则只能有一份有效的完整正文；其他位置保留短摘要和精确引用。
- 优先修改已有承载文件。确需新文档时，先确认没有同主题正文，再补入口，不创建孤立规范。
- 源码说明当前实现，规范表达已批准的业务意图。二者冲突时列明差异和证据，暂停相关语义修改并询问用户；不得默默改规范迎合缺陷，也不得仅凭文档擅改实现。
- 业务规则正文由 [business-constraints.md](business-constraints.md) 持有；日志、版本、审查分别由 [logging.md](logging.md)、[versioning.md](versioning.md)、[code-review.md](code-review.md) 持有。

<a id="doc-content"></a>
## 内容与表达

- 优先记录读代码不容易得到的意图、不变量、适用边界、取舍和例外。可直接查到的路由、字段、枚举、版本及文件清单引用源码，不再维护副本。
- 使用明确的“必须 / 禁止 / 建议”，写清适用对象；例外必须说明范围和理由，不能只写“特殊情况除外”。
- 历史事故只保留仍有效的约束、必要理由和原决策引用。调试过程和长篇复盘不进入每次会话默认加载的指南。
- 规则形态由 issue 决策塑造时，在首次陈述处标注首个决策号，后续改变形态的决策另行注明；源码可直接读出的事实不机械标号。
- 区分定义与实现细节、当前行为与计划、已验证与待验证。不能将建议写成已存在的能力。
- 示例只展示必要信息，优先引用现有实现及代表性测试；不得复制另一套财务公式或误用不同层的判据。
- 不为行数或 token 目标删掉业务例外、授权边界和关键原因，也不为凑行数添加空话。

<a id="doc-reading"></a>
## 按任务读取

1. 从根指南的任务加载表定位模块与专题，多类型任务取并集。
2. 先定位标题或符号，再读对应章节、实现及相关测试；信息不足才扩展范围。
3. CLI 先读命令索引，再读对应命令组；视觉相关任务才额外加载 visual-spec，非视觉任务仍读前端模块指南。
4. 不默认全文加载所有专题、CLI 手册、历史记录或其他 worktree；已委派的搜索不再重复执行。

<a id="doc-sync"></a>
## 何时同步

业务规则、公开契约、配置、运行前提、测试数据契约或操作流程变化时，必须同批更新：

- 持有规则的正文；
- 受影响的模块入口、源码注释及交叉引用；
- 对应生成产物与可执行验证。

PR 必须说明“已同步文档及位置”或“无需同步及理由”。不要求每个代码 PR 修改 Markdown；纯内部重构且外部约定不变时可说明无需同步。文档承诺必须有依据，不能用“已同步”替代检查。

<a id="doc-references"></a>
## 稳定引用

- 文档链接使用相对当前文件的仓库内路径；禁止将本机绝对路径或 `file:///` 地址写作共享入口。
- 长期跨文件规则引用使用显式稳定锚点（如 `rule-snapshot`）或稳定标题，不新增仅靠章节序号的引用；重命名或迁移时同批修复调用方。
- 源码引用以文件和符号定位。代码链接可指向文件，并注明 `文件::符号`；不要把源码行号当永久锚点。
- [错误码总表](business-constraints.md#错误码总表) 的标题、表结构及 `文件::符号` 格式是机器接口，不得随排版重构破坏。
- 该文档正文中，单独反引号包裹的大写下划线 token 被现有检查器视为错误码。非错误码常量应明确字段语境（例如 `market="CN_EXCHANGE"`），不要靠扩大豁免让检查变绿。

<a id="doc-migration"></a>
## 迁移与去重

1. 在任务记录中逐项确认旧规则的新落点，含理由、历史决策来源和例外；不另建永久迁移台账。
2. 合并到既有主题后删除旧完整正文，旧入口改为引用，不保留两份同时有效的说明。
3. 同批检索并修复模块指南、专题、runbook、模板和源码注释中的活动引用；本地工具薄适配也需核对，但不得擅改权限或将私有设置纳入版本控制。
4. 发现冲突先报告，不能在“文档整理”中改业务行为、删除保护禁令或扩大本次授权。

<a id="doc-verification"></a>
## 验证与交付

- 核对完整 diff：规则无遗漏、引用可定位、例外未丢失、生成产物没有手改。
- 从仓库运行 `python scripts/check_context_docs.py`；自测为 `python -m pytest scripts/tests/test_context_docs.py scripts/tests/test_ci_path_mapping.py -q`。受管文档与源码引用文件明确列在[检查器](../../scripts/check_context_docs.py)的 `MANAGED_DOCS` / `SOURCE_REFERENCES`，不递归扩展目标、不访问外部网站，也不涵盖被忽略的本地工具规则；目前识别普通行内 Markdown 链接、引用式链接定义、显式 ID 和 ATX 标题，代码围栏中的示例不当作入口。
- CI 的 changes job 在 checkout 后无条件运行此检查，docs-only PR 也不绕过；自测复用 Run scripts tests。错误码总表及源码符号继续由已有后端测试守门，不复制 AST 逻辑。
- 运行本次影响面的契约检查及相关测试；检查范围和局限必须明示。机械检查不能证明业务语义正确，仍需对照实现与测试核实。
- 分别报告通过、失败、未运行和无法验证，不能把计划执行写成执行完成，不能用 AI 自评代替证据。
- 不将凭证、真实投资数据、完整运行日志或会话转录写入文档。任务授权和临时例外不自动升级为永久权限或全项目规则。
